# 设计原则

## 核心判断

这个项目遵循的不是“只靠 prompt”的开发方式，而是 Harness Engineering。

核心思想：

- Agent 不需要一开始知道一切
- Agent 需要在正确时机拿到正确粒度的信息
- 上下文负责“告诉它知道什么”
- 约束负责“阻止它做不该做的事”

## 渐进式披露

上下文加载应分层，而不是一次堆满：

1. `AGENTS.md`
2. 对应目录的 `AGENTS.override.md`
3. `docs/` 中 1 到 2 份最相关控制面文档
4. 具体代码文件
5. 必要时再读取 skill、references、历史报告

规则：

- 不预载全部 docs
- 不预载全部 skills
- 不预载 skill 下所有参考资料
- 优先加载地图、索引、规则，再加载细节

## 上下文管理原则

好的上下文应该回答：

- 这是个什么任务
- 应该去哪里工作
- 当前有哪些约束
- 预期输出是什么

坏的上下文管理表现为：

- 想一次性给全量知识
- 让 Agent 自己猜边界
- 把无关信息和关键约束混在一起

## 架构约束原则

约束要显式、防止偏航，而不是只做背景介绍。

约束至少应防止：

- 选错模式
- 读错目录
- 写错位置
- 用错工具
- 静默改变事件合约
- 把有来源研究压缩成模糊总结

## 记忆策略

使用三层记忆：

### 短期记忆

- 会话消息
- 当前 todo
- 正在执行中的暂态信息

### 中期记忆

- tool logs
- turn 记录
- 运行轨迹

### 长期记忆

- 研究产物
- 知识条目
- 可复用的整理结果

规则：

- 搜索噪音不能直接进入长期记忆
- 凡是自称“研究结果”的输出，应留下可复用产物
- 长期记忆必须带上标题、分类、时间、来源依据

## 产物策略

好的产物应该：

- 可检查
- 可追溯
- 可复用
- 足够小，方便后续定位

优先形式：

- knowledge item
- markdown 报告
- 结构化评估结果

## 技能策略

每个 skill 应该：

- 范围窄
- 何时使用写清楚
- 依赖什么工具写清楚
- 引用资料按需加载
- 尽可能能被 eval

## 界面策略

前端不该只展示 token，而应展示工作流状态：

- 规划
- 子代理执行
- 工具调用
- 验证
- 产物写入
- 失败与回退

## 文档策略

文档是控制面，不是垃圾堆。

每份文档只回答一个问题：

- `ARCHITECTURE.md`：东西在哪里
- `DESIGN.md`：系统怎么工作
- `PLANS.md`：下一步先做什么
- `PRODUCT_SENSE.md`：为什么这样做
- `QUALITY_SCORE.md`：怎么判断好坏
- `RELIABILITY.md`：如何保持可靠
- `SECURITY.md`：什么不能做
- `ENTROPY_MANAGEMENT.md`：如何防止 Harness 变脏
