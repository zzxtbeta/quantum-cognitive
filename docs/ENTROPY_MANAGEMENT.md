# 熵管理

## 为什么要做

Harness 本身也是代码和文档，也会随时间腐化。

常见腐化表现：

- 规则文件越来越长，没人敢删
- 同一规则在多个地方重复出现，互相冲突
- 旧约束没有移除，Agent 读到过时指令
- 新错误只在聊天里提过，没有沉淀
- 说明文档和运行资料重新混在一起

熵管理的目标是：让约束系统本身不随时间退化。

## 主原则

### 1. 规则要有固定落点

- 项目专有控制面规则放 `docs/`
- 跨项目可迁移规则放 `harness/rules/COMMON_RULES.md`
- 新错误类型和对应约束放 `harness/rules/ERROR_PATTERNS.md`
- 临时高优先级覆盖放 `AGENTS.override.md`

### 2. 新错误先记录，再抽象

每次出现新的 AI 错误类型时：

1. 记录错误现象
2. 记录触发场景
3. 记录影响
4. 记录本次修复或补救策略
5. 如果重复出现，再抽象成长期规则

### 3. 过时规则必须删除

不要只增不减。

凡是出现以下情况，应考虑删除或重写：

- 指令已不适用于当前架构
- 更高层文件已经覆盖相同内容
- 同一规则被更准确的规则替代
- 执行者读完后仍无法知道该怎么做

### 4. 文档控制面要保持轻

- 根级 `AGENTS.md` 只做入口和路由，不堆背景
- `AGENTS.override.md` 只做局部边界，不复制总规则
- `docs/` 每份文档只回答一个问题
- 长背景材料不要污染控制面文档

### 5. 定期做防腐化清理

建议在较大阶段改动后做一次清理：

- 删除失效规则
- 合并重复规则
- 修正文档中的旧路径
- 把聊天中的经验回收到固定文件

## 自检清单

当你准备新增一条规则时，先问：

- 这条规则是项目专有，还是跨项目通用？
- 它是长期规则，还是临时覆盖？
- 它是否和现有规则重复？
- 它是否可以更短、更明确？
- 它是否真的能降低一个具体错误的发生率？

## 当前治理重点

1. 保持控制面文档中文、短小、分层明确。
2. 让新增错误类型有稳定记录位置。
3. 不允许 `docs/` 再次回到“杂项堆场”状态。
